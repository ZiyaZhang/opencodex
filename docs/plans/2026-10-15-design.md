# opencodex 重做方案

写于 2026-10-15 04:40 UTC。前置文档：[opencodex 问题清单](opencodex-review-2026-10-15.md)。并行在跑的是一份手工差距报告样例（会话 codex-gap-report），用来定报告模板，不影响本方案的结构。

## 一句话

每当 Codex 出新版本，自动收集它新增了什么，对照 DSH 现状写成差距报告；人挑中的条目一键开一个 DSH 创造模式会话去实现。opencodex 只负责发现、对照、交接，不再负责实现、验收和安装。

## 不做的事

- 不自动安装、不自动验收、不自动截图对比。
- 不做 token 账本、阶段额度、无进展门限、前台租约。成本看 DSH 会话自己的用量显示，限制只留"每天最多生成几份报告"。
- 不给研究会话造专用工具链。实现阶段用 DSH 原生的创造模式 skill、plugin_manager、cordis_inspect_query。

## 成功标准

| 项 | 标准 |
| --- | --- |
| 时效 | Codex 正式版发布后一天内，候选和报告出现在页面上 |
| 证据 | 报告里每条"Codex 怎么做"引用 PR、文件或 i18n key；每条"DSH 现状"给到 file:line，索引没命中就写"未找到"，不写"没有" |
| 成本 | 一条候选的报告生成不超过 3 万 token；一个正式版全部候选不超过 20 万 token |
| 人工 | 审一份报告不超过 10 分钟；一键开工后不用再手工搬证据 |

## 信号源

| 源 | 候选单位 | 取法 | 已核实的事实 |
| --- | --- | --- | --- |
| openai/codex releases | release notes 里 New Features 的每条，对应一到多个 PR | `gh api` 拉 release 正文，解析 `(#NNNNN)`，`gh pr view --json files,body`，需要时 `gh pr diff` 只取选定文件 | 正式版每周两到三个；notes 是 release-please 格式，分 New Features / Bug Fixes / Chores，附完整 PR 列表；0.161→0.162 共 227 个提交、1.1 万行改动，不能整包读；一个功能 PR 约 14 个文件、1,200 行 |
| openai/codex 结构性文件 | 文件级 diff | 跟踪 `codex-rs/features/src/*.rs`（功能开关注册表）、`codex-rs/app-server-protocol/schema/typescript/*.ts`（协议类型）、`docs/*.md`、`codex-rs/config.md` | 这四处的 diff 是"有没有新功能面"的确定性信号，不依赖 notes 写法 |
| ChatGPT.app（Codex 桌面端） | 版本号变化 | 监听 `Contents/Info.plist` 的 CFBundleVersion；变了就给 `Resources/app.asar` 做清单快照（路径、大小、hash），再对任一 locale bundle 做 i18n key 与字符串 diff；chunk 名新增单列 | 清单约 2.1 万文件；locale bundle 里有 3 万条字符串，键名带功能名，例如 `codex.command.composer.captureAppshot`；chunk 名直接带功能，例如 `page-codex-quick-chat-*`、`shared-codex-snapshot-*`；Info.plist 没有 Sparkle 订阅地址，只能监文件 |
| 官方 RSS | 公告条 | 保留现有 changelog-parser，去掉 CLI 过滤 | 只做云端和产品公告的分类与触发，不当候选主来源 |

深挖是按需的：人点"深挖"时才对 app.asar 跑 rea 的 `analyze-javascript-application` 和 `compare-application-versions`（命令行、离线、Node 24 已装），结果作为附件进报告。rea 不以 MCP 形式接进会话：它有 172 个工具，schema 近 500 KB，接进去每次请求先吃掉十几万 token。

## 流水线

| 阶段 | 用不用模型 | 输入 | 输出 |
| --- | --- | --- | --- |
| A 采集 | 不用 | 三路信号 | `candidates/<id>.json`：标题、来源、证据引用、原文片段 |
| B 归类 | Flash，一批一次 | 候选列表 | 分类（CLI 核心 / 桌面端 / 云端 / 模型公告 / 修复）、与 DSH 的相关度、同一功能多信号合并 |
| C DSH 索引 | 不用，每天随镜像刷新 | 官方镜像 | 388 个包 README 的 Summary、docs/config-catalog.md 条目、.agents/notes 的标题和状态、docs 目录；rg 可检索 |
| D 差距报告 | V4-Pro，每条候选一次 | 候选证据包 + 索引命中的三到五段 README 和源码定位 | 固定模板一段：Codex 做法 / DSH 现状 / 差距与扩展点 / 工作量 / 建议级别 |
| E 开工 | 交给 DSH | 人勾选的报告 | 新建会话：creator 预设，首条消息是报告加任务说明；之后 opencodex 不再介入 |

D 阶段的证据包有上限：PR 正文加文件清单加选定文件的 diff 不超过 1.5 万 token，超出就按文件相关度截断并在报告里注明没读的文件。模板强制引用，空引用的句子不允许出现。

## 产品形态

一个 DSH 第三方插件，沿用 OpenCodex 这个名字和仓库。

- Host：三个采集器、索引构建、候选库、报告生成调度、开工动作。报告生成通过 `sessionController.create` 起一个分析会话（或直接 llm 调用，待选），cwd 指向候选的证据目录。
- Client：一页。候选列表按来源、分类、相关度、状态筛选；报告阅读；按钮只有检查更新、生成报告、深挖、开工、忽略。设置只有频道、监控路径、模型、每日报告条数上限。
- 存储：`$DSH_HOME/opencodex/{snapshots,candidates,reports,index}`，全部明文 JSON 和 Markdown。候选状态四个：new、reported、started、ignored。
- 开工会话的 cwd 和预设见待定项 E。创造模式路径下，产物是能装进她 profile 的独立 bundle；需要改核心的条目标"需要 PR"，另开 dev clone 会话。

## 分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| 0 进行中 | 手工做五条功能的差距报告样例 | 定下报告模板和"DSH 现状"的证据写法 |
| 1 | 采集脚本、候选库、DSH 索引，命令行可跑，无 UI | 对最近三个正式版和当前 app 版本跑一遍，候选 JSON 齐全，每条都有证据引用 |
| 2 | B 归类和 D 报告生成 | 对十条候选生成报告，人工打分：证据到位、DSH 现状准确、工作量估计合理；单条成本在上限内 |
| 3 | 插件页面、定时、开工按钮 | 装进她的 profile 用一周，至少一条候选从发现走到开工 |
| 4 按需 | rea 深挖、CUA 截图参考、alpha 频道、Codex IDE 扩展 | 各自单独定 |

每期结束先给她看结果再进下一期，和实验的做法一样。

## 成本

| 项 | 估计 |
| --- | --- |
| 一条候选的报告 | 1.5 到 3 万 token，V4-Pro |
| 一个正式版（约六条功能） | 10 到 20 万 token |
| 一个月（约十个正式版加桌面端两三次） | 150 万 token 上下 |
| 索引构建、采集、清单 diff | 不用模型 |

作为对照，旧版一次失败运行就是 172 万。

## 风险

- 合规：只在本机分析 app.asar，报告只写行为描述、文件名和 key 名，不复制代码，不分发包内容。rea 的免责声明是同一立场。
- OpenAI 变动：资产加密或去掉 i18n key 时退回源码加 RSS；notes 格式变时以 PR 列表为准。
- 噪声：alpha 版几乎每天发，默认只跟正式版；桌面端 locale 里 ChatGPT 的字符串远多于 Codex，只取 `codex.` 前缀的 key。
- 模型编造：模板强制引用；索引没命中就写"未找到"；报告生成会话只给证据目录的读权限。
- 网络：保留代理处理；gh 已登录；GitHub API 限额按小时算，采集频率一天一次够用。
