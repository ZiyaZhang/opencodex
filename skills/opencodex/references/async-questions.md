# Questions that preserve the composer

Scope the feature as two related contracts: question delivery/answer routing and independent composer availability. First inspect the installed DSH question lifecycle; reusing its request IDs, timed answers and late-answer semantics is preferable to introducing a second question service.

A pending card must not replace the normal composer, clear its draft, capture unrelated Enter presses, remove attachments, or change a message into an answer. Submitting the card resolves only its question ID; sending an ordinary message keeps its ordinary meaning. Preserve accessible labels and a keyboard path between the card and composer.

Determine blocking semantics per question. Optional clarification may let independent work continue. A required answer still gates dependent actions even though the composer stays usable. A timeout is not an answer. Cancellation, expiry and late answers need explicit states; do not silently attach a late answer to a newer question with the same label.

Acceptance fixture: keep an unsent draft and one synthetic attachment; trigger question Q1, send an unrelated message, then answer Q1. Trigger Q2 before a delayed Q1 reply, refresh, and verify the correct IDs and drafts survive. Repeat with an optional and a required question. Test duplicate clicks, keyboard submission, session switching, and plugin unloading.

Measure the card and composer together at wide and narrow viewports in both supported themes. Record differences from the target reference instead of claiming equivalence from one screenshot. This is a generated-feature validation target, not a statement that OpenCodex itself ships an async-question replacement.

## Concrete DSH 0.2.1-alpha.2 investigation map

Start with installed public package declarations, not guesses:

- `@deepseek-ai/dsh-client-ui-conversation/lib/types/client/contract/slots.d.ts`: `conversation.composer` is a chain; `conversation.composer.dock` is a session-scoped list. `conversation.input.dock` is above the resident input card.
- `@deepseek-ai/dsh-client-ui-session/client`: `PropsRuntime` on a session slot includes `sessionId` and `useSessionStatus`. The selector can inspect `snapshot.get(sessionId)?.pendingInteraction?.kind`. Built-in question kind is `question`; plan decisions use `plan-review` and must retain their approval semantics.
- `@deepseek-ai/dsh-client-ui-user-questions/client` exports **types**, including PendingQuestion. Do not runtime-import its private component or instantiate a second service. Its contract preserves the request, countdown, draft answers and late RPC answer channel.
- `@deepseek-ai/dsh-user-questions/types` describes projection rows; `@deepseek-ai/dsh-user-questions/remote` declares `answer(agentId, callId, answer)` returning `RemoteResult<boolean>`. Never interpret `{ok:false}` as successful submission. The continued-question answer RPC is not a substitute for a still-blocking waterfall request.

For a minimal layout-only reconstruction, first verify the installed renderer's actual DOM: it retains the ordinary input tree inside `[data-chain-overlay-fallback="conversation.composer"]`, hiding that wrapper with inline `display:none` while a chain entry wins. That is why the draft can survive even though it is unavailable. The conversation has `[data-composer-seat]` and `[data-conversation-session]` anchors. These are version-sensitive seams: verify the exact installed version/DOM, scope any styling to the current session's **question** state, and fail inert if the expected anchor is absent. Never reveal all hidden composer fallbacks globally: some hide for approvals, offline parent sessions or other deliberate blockers.

A small contribution to `conversation.composer.dock` can observe the existing question state and publish a session-local marker. A stylesheet scoped through that marker can preserve the resident composer alongside the existing question card, leaving the built-in question owner responsible for submission, timeout and late answers. This is one bounded strategy to evaluate, not a preapproved implementation or a claim that the target Codex layout is identical. Verify that the chosen selector does not match another session or a plan-review and that unloading removes the marker/style and restores the default takeover.

### Bound the implementation to the layout change

1. Use `PropsRuntime<'conversation.composer.dock'>` from the public slot package. Load declaration augmentation with type-only imports from the public conversation and session `/client` exports. The component receives `sessionId` and `useSessionStatus`; select the primitive `snapshot.get(sessionId)?.pendingInteraction?.kind === 'question'`. Keep hooks unconditional and render the marker only when that selector is true.
2. Register a unique list entry through `ctx.slots.inject('conversation.composer.dock', () => ctx.slots.register(...))`. This dock is inside the retained resident input tree, so it remains mounted even when the wrapper is hidden. A hidden marker still participates in CSS `:has()` matching; it does not need to be a visible extra row.
3. Scope every selector through the marker's own `[data-composer-seat]` and the direct `[data-slot="conversation.composer"]` outlet. Override only the matching `[data-chain-overlay-fallback="conversation.composer"]` display. The wrapper has an inline display value, so an ordinary stylesheet rule without sufficient priority will not reveal it. Do not remove `hidden`, `inert`, or `disabled` from arbitrary descendants.
4. Inspect the actual order. The renderer emits fallback **before** the elected question; the composer seat is a column flex container and outlet wrappers use `display:contents`. If the question should sit above the composer, order the scoped `[data-question-key]` card before the retained input in that seat. Account for the intervening `data-slot` wrapper; a selector assuming the card is a direct DOM child of the seat is wrong. Do not target generated CSS class hashes. Check visual order **and** keyboard focus order; CSS ordering alone does not change the latter.
5. Put the stylesheet in a context effect that removes exactly its own style element on unload. Let the slot registry own component disposal. Do not move React-owned DOM nodes, replace the editor, call private card methods, or publish a second pending interaction.
6. If the expected renderer anchors are missing, leave the native UI intact and report an unsupported version. Pin the generated package's tested DSH versions; these DOM anchors are an inspected compatibility seam, not a promise about future releases.

The feature package must not use OpenCodex's research-job service at runtime. It is an independent layout plugin: users should be able to keep it after removing OpenCodex. See [DSH packaging and loader recipe](dsh-adaptation.md) for the Host stub, Client manifest, module wrapper, shared externals and lifecycle rules.

An alternative replacing the whole question UI is substantially larger: it must own the forwarded `user-questions/request` waterfall, claim/release, timed countdown, persisted projection, late-answer RPC and teardown delegation. Do not choose it merely to move a card. `PendingQuestion.dismiss()` is not a universal hide operation: unnamed blocking questions may be **cancelled** by dismissal.

Package the resulting feature separately from OpenCodex with its own `dsh.bundle.patch` and compiled Client entry. Its build must externalize shared React and Cordis; DSH's module wrapper calls `window.__ModuleLoader__.load({id,factory})`. Lifecycle effects and slot registrations belong to the plugin context. A pure Client layout contribution can have a minimal Host entry that only activates its Client half.

## Real acceptance sequence

Build and pack the feature inside the research workspace, then install that tarball in a dedicated test profile. Do not call the implementation accepted merely because a synthetic page shows two boxes. Run these steps in the real DSH UI with an ordinary root session, configured model and actual `ask_user_question` tool:

1. **Default control:** with the feature disabled, trigger a two-choice blocking question. Record its question key/call ID and show that the native fallback is hidden. Record the supported DSH version and profile.
2. **Editable input and draft preservation:** enable the feature, verify the same question card and resident editor coexist, and enter `DRAFT-KEEP-27` plus one synthetic attachment without sending. Click a question choice and submit its answer. Verify the ordinary draft and attachment remain, and the question answer follows the question's original ID.
3. **Actual ordinary sending while waiting:** trigger Q2 and leave it unanswered. In the ordinary composer, enter `QUEUE-MSG-42` and use its normal Queue/Send action. Verify the queued-message row or real session inbox receipt contains exactly that text; verify Q2 remains unanswered with the same key. Then type `DRAFT-AFTER-SEND-43`, answer Q2, and verify this new unsent draft survives. Clearing the draft that was intentionally sent is correct behavior. A visible button or an optimistic click is not a successful send receipt.
4. **Keyboard and focus:** repeat the ordinary send with Enter; repeat question submission from its custom-answer field. Neither should submit the other. Tab between both surfaces, check narrow-window scrolling, and verify no focus trap or invisible focused editor remains.
5. **Distinct continuation semantics:** configure a timed question using the installed tool's actual schema/settings. Let it expire without interacting with its answer field, then submit a late answer. Verify the original call ID, persisted outcome and late-answer routing. A blocking question may continue blocking model work while its composer works; this layout plugin does not change that. Queue acceptance is not evidence of immediate agent continuation.
6. **Isolation and restoration:** switch between a questioning session A and ordinary session B; include an embedded or second view when available. Test a plan-review card and any explicit composer block: the feature must not reveal or enable those inputs. Reload while Q3 is pending. Finally disable/uninstall only this feature plugin while Q3 waits: the native takeover returns, the fallback hides, the question remains answerable, and re-enabling restores the unchanged ordinary draft.

Capture wide and narrow screenshots of the card plus composer and of default restoration. Save the observed send receipt, question ID correspondence, package hash and test steps as separate evidence. Record target visual comparison as unknown when no target reference is accessible; functional acceptance can still establish that the generated DSH feature works, without inventing a Codex screenshot comparison.
